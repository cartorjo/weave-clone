# Emposo website - project instructions (technical track)

## Scope of this team
This team improves the Emposo site on aesthetics and the technical side only:
visual polish, UX and information architecture, frontend code, component
standardization, technical SEO, accessibility and performance. It does NOT
write, rewrite or propose copy, messaging, content strategy or claims.

**Copy** means every human-readable string: visible text, alt, aria-label and
screen-reader-only text, title and meta descriptions, OG/Twitter and JSON-LD
text fields, form and error messages (including those in js/), email subjects.
Existing copy is fixed input. When a change needs a string that does not exist,
insert "[TEXT: owner]" and list it under NEEDS-OWNER; never draft it.
Enforced: `npm run check` runs `check:copy`, which fails on any added or
removed string versus tools/copy-baseline.json. Only owner-approved wording is
accepted with `npm run copy:accept`, and the baseline diff in the PR is what the
owner reviews. Moves and reorders pass.

See @README.md for build details. Backlog: @docs/backlog.md. Components:
@docs/components.md. Benchmark patterns: @docs/review/benchmark-patterns.md.

## Commands
- npm run dev - assemble + tailwind watch + local server on 8080
- npm run build - assemble + CSS (committed outputs)
- npm run check - build reproducible, links/anchors/images/redirects/legacy
  URLs, head tags + JSON-LD, copy unchanged; must exit 0 before every commit
- npm run smoke - browser smoke against :8080 (overflow, console, CSP, axe, flows)
- npm run visual:snapshot / visual:diff / visual:pixdiff - parity evidence
- npm run css:shadowed - declarations fully overridden by a later identical selector
- npm run build:dist / npm start - production webroot dist/ (only shipped files)
- npm run build:img - responsive images from assets/src/

## Architecture
- partials/ - head, header (skip link, nav, mobile menu), footer, contact-form.
  Navigation is edited only here.
- pages/*.html - subpage main content only; sections/*.html - homepage fragments,
  ordered in pages.mjs. All shipped HTML is generated by assemble.mjs; never edit it.
  Page sources use <page-hero …> and <page-crumb label> for the shared frames
  (expanded by assemble.mjs via content/render.mjs); never hand-write them.
- pages.mjs - route, title, description, nav key, scripts per page.
- content/site-data.mjs - data (read-only for this team except structural fields).
- content/render.mjs - shared renderers (the component layer); variants are
  parameters, never copied markup (e.g. cta(name), chip(), picture()).
- styles/main.css - tokens (@theme: colors, type roles, breakpoints, radius;
  :root: --space-* steps, motion, scrims). Component canon:
  styles/11-components.css (imported last). 07-10 hold older per-area CSS.
- docs/components.md - component canon and contracts (German; owned by
  design-system-engineer). Contract template at its end.
- tools/ - check-content, check-meta, check-copy, build-dist, visual/.

## Two kinds of change
- Refactor (no visual change intended): visual:diff before/after must show 0
  style transitions; say so with the numbers in the handoff and commit.
- Aesthetic (visual change intended): before/after screenshots per affected page
  and width (visual:pixdiff crops) attached to the handoff; the owner approves
  before merge. Only the intended transitions may appear in visual:diff.

## Benchmark learnings we apply (patterns, not copy)
Benchmark: mckinsey.com. Structure and behaviour only.
1. No dead ends: every page ends with related content and a context CTA.
   (Exception by owner decision 24.09: industry tiles are static, not links.)
2. Repeatable templates: page hero -> body sections -> related -> CTA.
3. Complete, unique metadata per page (canonical, OG, Twitter, share image,
   JSON-LD, lang) - enforced by check:meta.
4. Semantic headings (one H1, no skipped levels), never heading levels for size.
5. Numbers and text in static HTML; motion is an enhancement, off under
   prefers-reduced-motion; no content depends on JavaScript.
6. Anti-patterns to avoid: placeholder share images, empty alt on content
   images, duplicated H1 for desktop/mobile, counters at "0" without JS.

## Non-negotiables
- Zero third-party requests (GDPR; strict CSP in serve.json). No inline
  <script>/<style>/style="" in shipped HTML (JSON-LD data blocks excepted).
- html { font-size: 100% } stays; never a vw-scaled root.
- Tokens only: ink #0A0532, orange #F7911E (decorative), info #4597CE,
  self-hosted Roboto 300-700. New values become tokens; Tailwind --spacing-<n>
  names are forbidden (they override numeric utilities) - use --space-*.
- Heroes: fetchpriority="high", never lazy. Other images: picture with
  AVIF/WebP + JPEG, width/height set, loading="lazy".
- Indexing: every host sends X-Robots-Tag noindex unless the deployment sets
  INDEXABLE=true (only emposo.de at launch). Never set it elsewhere.
- Owner decisions are not reversed (docs/components.md, docs/backlog.md
  "Owner decisions"); propose changes as NEEDS-OWNER items instead.

## Coordinator role
The main session coordinates (or: claude --agent site-coordinator). It plans,
delegates, integrates and reports.

Delegation map:
- ux-ia-architect - IA, navigation, templates, interaction patterns, link map.
- design-system-engineer - tokens, component contracts, CSS architecture,
  renderers in content/render.mjs, docs/components.md, aesthetic changes.
- frontend-engineer - partials, pages, sections, JS, build/check scripts, images.
- seo-specialist - head tags, JSON-LD, sitemap, robots, redirects, crawlability.
- a11y-perf-reviewer - WCAG 2.2 AA, keyboard, focus, contrast, motion, no-JS,
  image weight, loading.
- qa-reviewer - final gate: runs the gates, checks acceptance, PASS or FAIL.

## Workflow per backlog item
- S items: coordinator writes docs/handoffs/<ID>.md -> owning engineer ->
  qa-reviewer.
- M/L items: ux-ia-architect and/or design-system-engineer -> frontend-engineer
  -> seo-specialist and a11y-perf-reviewer (parallel) -> qa-reviewer.
- Each agent appends its section: what changed, files, evidence, status (DONE /
  BLOCKED / NEEDS-OWNER). On FAIL route fixes to the owner agent (max 2 loops,
  then NEEDS-OWNER).
- One item per commit: "<type>(<scope>): <summary> [B-xx]"; update the backlog
  with the commit hash.

## Definition of done (every item)
- Acceptance criteria met with evidence (path, snippet or command output).
- npm run check exits 0 (includes copy and metadata gates); npm run smoke passes.
- Refactor: visual:diff 0 transitions. Aesthetic: screenshots attached, owner
  approval recorded.
- No new third-party requests, no copy changes, tokens only.
- docs/backlog.md and, if components changed, docs/components.md updated.

## Design-system migration (from 2026-09-27)
Brief, verbatim: docs/design-system-brief.md (agents cite it as "brief §n").
Goal: move the UI layer off Material 3 naming and patterns onto composable
headless primitives and a Tailwind v4 semantic-token system. Copy and visual
design intent don't change, and the site stays deployable after every step.
Steps are Kind R (visual:diff 0). A step becomes Kind A only through a new owner
decision.

Roster (definitions in .claude/agents/)
- auditor: read-only inventory and scoring.
- token-architect: token work, strictly serial.
- tooling-engineer: replaces tailwind-migrator (no v3->v4 upgrade needed).
  Tailwind plumbing, lint, CI, harness.
- component-refactorer: one instance per leaf family.
- interactive-refactorer: the interactive components.
- a11y-perf-reviewer: the brief's a11y-reviewer.
- visual-qa, bundle-analyst, docs-writer.
- qa-reviewer: final gate.

Repo adaptation of brief §2 (owner confirmed 2026-09-27)
- No component framework (static HTML from assemble.mjs, vanilla JS).
  Interactive components are hand-built primitives on native elements and
  WAI-ARIA APG patterns, with Headless UI v2's data-* contract, listed as
  maintained components.
- Parts, cva variants and cn run at build time in content/render.mjs. cn is
  tailwind-merge extended with every custom @theme key. Attribute passthrough
  stands in for ref forwarding.
- No new runtime JS dependency without owner approval.
- Tailwind is already v4.3 and CSS-first, so there's no upgrade step. Numeric
  --spacing-<n> stays forbidden.
- Owner decisions, 2026-09-27:
  - Roboto stays as the brand face: a documented brand exception, so
    criterion 1 is scored at most 4.
  - The supplied Hays Glow icons stay; no lucide.
  - [data-theme="dark"] scopes today's navy sections. The page-level
    prefers-color-scheme fallback is built dark-ready but stays off until the
    owner approves a dark design.
  - The tokens README is styles/README.md.
  - Every DS step is Kind R.
- Ownership until Phase 5 closes: styles/, content/render.mjs,
  docs/components.md and tools/visual/ change through DS steps. Tech-track
  changes to them land on main between steps, after checking with the
  coordinator, and open steps rebase onto them. token-architect.md supersedes
  design-system-engineer's token rules.

Progress bar (brief §5)
- Every coordinator message to the owner starts with
  `[<20 chars: # done, - left>] <int>% | Phase <p>/5 | step <s>/<t>: <name>`,
  plus ` | WAITING FOR APPROVAL` while waiting.
- Weights: P1 5, P2 15, P3 10, P4 65, P5 5. P4 is split by the approved
  diff-size estimates; when the plan changes, recompute and say so in the line.
- A step counts only once it's merged with build, lint, tests, a11y and visual
  QA passed.
- The coordinator stops for the owner after Phases 1, 2 and 3.
- The line and a per-step checklist are mirrored to docs/PROGRESS.md on every
  state change: opened, in review, FAIL, BLOCKED, NEEDS-OWNER, waiting, merged.
- One report line per completed step.
- Subagents never print the bar or edit docs/PROGRESS.md.

Hand-off rules
1. Open a step. The coordinator creates branch ds/<n>-<slug> in worktree
   ../weave-clone-ds-<n> from current origin/main, runs npm ci there and
   records the exit code. It then writes docs/handoffs/DS-<n>.md from the DS
   template in docs/handoffs/README.md. DS-<n>.md stays untracked until the
   merge commit.
2. visual-qa captures the baseline from the untouched worktree before the
   implementer starts.
3. One implementer per step. Token work is always serial. Leaf families run in
   parallel worktrees only after the semantic layer has merged. The
   implementer commits sources plus regenerated outputs (npm run build) on
   the step branch, runs npm run check on the clean tree, lists every
   deletion, and returns its section.
4. The coordinator runs npm run build:dist once and serves the step and base
   ports. Then it dispatches, in parallel: a11y-perf-reviewer, visual-qa, and
   bundle-analyst (when the step deletes anything or changes CSS, JS, fonts or
   packages). qa-reviewer goes last. Reviewers return reports, and the
   coordinator pastes each under "## <agent>" in DS-<n>.md.
5. On FAIL the step goes back to the implementer, at most twice, then it's
   BLOCKED. An interactive replacement merges only on a11y PASS. A deletion
   needs bundle-analyst's proof, or it becomes NEEDS-OWNER.
6. Merge. Branches land one at a time. Each one rebases onto origin/main,
   regenerates outputs with npm run build (never hand-merge css/site.css,
   *.html or sitemap.xml) and reruns the gates. Evidence from before the
   rebase doesn't count. Each step is one squash commit:
   "<type>(ds): <summary> [DS-<n>]". After the merge, the coordinator checks
   the Railway deploy and commits the docs/PROGRESS.md update, and docs-writer
   appends to docs/design-system-migration-log.md.
7. Evidence goes to /Users/jose/workspace/emposo-new-website/ds-migration-run/
   <DS-n>/ in the local docs repo (gitignored), never into this repo.
8. tooling-engineer's harness step comes before the first token step:
   --scheme, 1440 px, pinned Lighthouse, fail on missing selectors. Until the
   owner approves a page-level dark theme, "dark" means the [data-theme="dark"]
   scopes captured with --scheme=dark.
